Orientation

How to use this

This package documents TrainHeroic as it actually is, and proposes a data model that removes its central constraint. It is written to be read by an implementing agent or engineer — everything is either observed, inferred, or explicitly flagged unknown.

VERIFIED

Observed directly in the live coach app, or quoted from TrainHeroic's official support documentation.

INFERRED

Reasoned from observed behaviour. Plausible, load-bearing in places — but not stated by TrainHeroic.

UNKNOWN

Genuinely undocumented. Searched official docs, blog, forums, review sites. No public source exists.

Read this before copying anything

The UI reconstruction in A3 is layout-faithful, not byte-identical — it was rebuilt from screenshots without access to TrainHeroic's source, fonts, or assets, and carries neutral branding deliberately.

Copy their layout logic, which is genuinely good. Do not copy their data model, which is where every limitation in this document originates. Sections A4 and D2 are deliberately placed side by side so the difference is visible.

The structural defect, stated plainly

Six of the twenty members exist only because unit is baked into identity. Weight (lb) and Weight (kg) are not the same metric rendered differently — they are different enum values. Any athlete who switches units, or any coach with athletes on both, is a data-migration problem rather than a display preference.

Part B · Flows

B1 · Session state machine

Most of TrainHeroic's data-loss reports live in the gaps between these states. STATES VERIFIED

Dashed = states TrainHeroic does not distinguish, and should. There is no observable difference between a session an athlete skipped and one they never opened, which is precisely why their Compliance report has no published definition.
Gotcha · publish timezone

Auto-publish runs in the coach's account timezone — the dialog reads "Central timezone (America/Chicago)" with no athlete-local option. Schedule publish jobs in the athlete's timezone, or at minimum the calendar's declared one. Ten lines now; a migration later.

Gotcha · snapshot on publish

The orange loop is the dangerous one. If percentages resolve at read time against the current working max, an athlete opening last month's session sees loads that were never prescribed. Resolve once, at publish, and persist.

B3 · Offline write path

This is where TrainHeroic bleeds. The recurring store-review complaint — "logged a workout, closed the app, it was gone" — has one signature. DIAGNOSIS INFERRED

✗ The failure mode

set entered → React state
set entered → React state
set entered → React state
⟵ app backgrounded · OS reclaims memory
everything lost

"Finish Session" is the first durable write. Everything before it is volatile.

✓ What to build instead

set entered → local DB (uuid v4, client-gen)
→ outbox queue
→ optimistic UI
→ background sync (retry, backoff)
server upsert on client id — idempotent

Client-generated IDs make every write replay-safe. Session finish becomes one more queued event, not a save point.

The video exception

Offline logging works in TrainHeroic; video is the documented exception. The cause is structural, not incidental — the exercise video field is a YouTube or Vimeo URL (confirmed in the Create Exercise form; there is no upload control). A third-party embed can never be cached. If offline demos matter — and in a gym basement they do — you need first-party transcoded assets. That is a real cost TrainHeroic dodged and now cannot recover from.

Part C · Analytics

C1 · Estimated 1RM

The most consequential finding in the teardown. TrainHeroic does not use a formula — it uses a lookup table, and the table runs out before their input range does.

Verified — direct quote

"Estimated 1RM are calculated directly from the NSCA load chart, based on the best effort of 15 reps or less." VERIFIED

The published NSCA chart maps reps to %1RM discretely. It defines 1–10 and 12. It does not define 11, and it does not define 13, 14 or 15 — the range TrainHeroic accepts. What happens in that gap is UNKNOWN; no public source describes it.

Implied 1RM from a 100 kg set
Same input set, three methods. Where they disagree is where your athletes' percentages disagree.
RepsNSCA chartEpleyBrzyckiSpread
All three converge near 10 reps and diverge hard at both ends. At 15 reps Brzycki reads 13.6 kg higher than Epley on the same set — and NSCA reads nothing at all.

What the chart shows

  • 1 rep: Epley returns 103.3 for a set that is a 1RM. A known artefact — it is not calibrated at r = 1. Special-case it.
  • 10 reps: all three land on 133.3. Total agreement, by coincidence of construction.
  • 12 reps: NSCA's last defined point. Brzycki has already pulled 4 kg above Epley.
  • 13–15 reps: NSCA is undefined. TrainHeroic still accepts these inputs.

Recommendation — 8/10 confidence

Ship Epley as the default, with a per-exercise override, and store the formula id alongside every computed value.

  • Continuous — 13/14/15 reps aren't a cliff
  • Most widely recognised — athletes can sanity-check you
  • Monotonic and differentiable — matters when you plot e1RM over time
  • Storing the formula id keeps history reproducible when you change the default

The trap · question polarity

Whether stress and soreness are reverse-scored before averaging is UNKNOWN — never stated. INFERRED the questions are worded so 5 always means "best", otherwise the mean is meaningless. If you let coaches author custom readiness questions you must store a polarity flag per question, or your averages silently invert and nobody notices for months.

Part C · Analytics

C3 · Volume · Intensity · Compliance

TrainHeroic names all three on the coach dashboard and defines none of them. ALL UNDOCUMENTED — the formulas below are mine, not theirs. Do not cite them as "how TrainHeroic does it".

Volume — stop computing one number

Tonnage only counts loaded work, so a session of 400 calories on an Assault Bike scores zero. Compute three separate series and never sum across them.

SeriesDefinitionCovers
tonnage_kgΣ(reps × load_kg) over sets where the metric is load-bearingBarbell, dumbbell, machine
work_repsΣ(reps) over unloaded setsCalisthenics, plyometrics
conditioning_loadΣ(duration_s × sRPE)The standard session-RPE training-load unit — the only thing that meaningfully compares a bike interval to a squat

Intensity

Two of my session cards showed – for Intensity, and both were sessions with no percentage-based prescriptions. INFERRED Intensity is average %1RM, null when nothing was prescribed as a percentage.

// rep-weighted, NOT the mean of set percentages —
// a naive mean over-weights warm-up singles
intensity = Σ(reps × load) / Σ(reps) / working_max

Compliance

TrainHeroic confirms two levels and gives no formula. Define yours in the UI, because coaches will otherwise assume the flattering one.

MetricDefinition
session_compliancecompleted sessions ÷ assigned sessions, where "completed" means Finish Session was pressed
block_compliancecompleted blocks ÷ assigned blocks, where a block is complete when every non-optional set in it has a result
Why the Optional column exists

That Optional member in the metric enum isn't a null placeholder — it is there so optional sets don't tank compliance. Small feature; it's what makes the number honest. Honour it.

C4 · Load rounding

72.5% of a 315 lb max is 228.375 lb. Nobody has written down what TrainHeroic shows the athlete. UNKNOWN — and it is the single most-encountered calculation in the entire product.

displayed_load = round_to_increment(target_pct × working_max, increment)

// increment resolves: exercise → equipment type → account default
EquipmentIncrementNote
Barbell (kg)2.5 kg1.0 kg if micro-plates are declared available
Barbell (lb)5 lb2.5 lb with fractional plates
Dumbbell—Snap to the gym's actual rack, a declared array — not an increment
Machine / cable—Snap to the declared stack increment
Fixed / bodyweightnoneNo rounding
Two rules

Round down by default for percentage work — never prescribe more than intended. And always expose the exact unrounded value on long-press, so a coach can audit it.

Storing equipment_increment on the exercise is about ten minutes of work and eliminates an entire category of "the app told me to load 228.375 lb" support ticket.

Part D · Proposed schema

D1 · The 2-metric ceiling

One design decision generates every limitation in this document. Here it is, and here is what replaces it.

✗ Fixed-arity row — TrainHeroic

set = { ordinal, param_1, param_2 }

-- prescription table is literally 3 columns
[ Set # ][ Parameter 1 ][ Parameter 2 ]

Cannot express: tempo · rest as data · reps + weight + RPE together · a load range · an RPE range · anything conditioning-shaped.

Downstream: unit variants become separate enum members, so unit conversion is a data-model problem instead of a display problem. And conditioning has nowhere to go, so it goes into free text — which is invisible to every analytics report they ship.

✓ Open bag of typed metrics

set = {
  ordinal,
  targets: [ {metric, resolution} … ]   -- n
}

-- one row per metric. no arity limit.
reps · load · rpe · tempo · rest  →  5 rows

Metrics become data, not an enum. A new metric is a row in a registry table, not a migration and a deploy.

Units become display, not identity. Weight (lb) and Weight (kg) collapse into one metric load, stored in kg. That alone removes six of their twenty enum members.

If you take one thing from this package

Model a set as an open bag of typed metrics from day one. It costs you almost nothing now — the tables below are not complicated — and it is genuinely unfixable later, because every prescription, every result, every report and every export encodes the arity assumption.

Gotcha · graph cycles

reference_max and track_as are graph edges and must be cycle-checked on write, not on read. A→B→A will hang your resolver. Enforce depth ≤ 1 unless you have a compelling reason — full transitive resolution is a support nightmare when a coach can't work out why their percentages moved.

Gotcha · nullable parent

performed_set.prescribed_set_id is nullable on purpose. An athlete-added set has no parent. If you make it required you have re-created TrainHeroic's positional model and you will not be able to tell "skipped" from "never reached" — which is exactly why their Compliance report has no published definition.

-- ═══ METRIC REGISTRY — data, not enum. New metrics are rows. ═══
CREATE TABLE metric (
  key              text PRIMARY KEY,        -- 'load','reps','rpe','tempo','rest'
  dimension        text NOT NULL,           -- mass|count|ratio|time|length|power|velocity|energy
  canonical_unit   text NOT NULL,           -- kg|rep|rpe|s|m|W|m/s|kcal
  value_type       text NOT NULL,           -- scalar|range|tuple|duration|bool
  aggregation      text NOT NULL,           -- sum|mean|max|min|last|none  → analytics for free
  higher_is_better boolean,                    -- NULL = neither (tempo)
  is_load_bearing  boolean NOT NULL DEFAULT false
);

-- ═══ EXERCISE + the two indirection edges worth stealing ═══
CREATE TABLE exercise (
  id                        uuid PRIMARY KEY,
  owner_id                  uuid,                 -- NULL = global library
  name                      text NOT NULL,
  video_asset_id            uuid,                 -- first-party + cacheable, NOT a YouTube URL
  cues                      text,                 -- "Points of Performance"
  equipment_id              uuid REFERENCES equipment(id),
  default_metrics           text[] NOT NULL,     -- a DEFAULT, not a ceiling
  reference_max_exercise_id uuid REFERENCES exercise(id),
  track_as_exercise_id      uuid REFERENCES exercise(id),
  CHECK (id <> reference_max_exercise_id),
  CHECK (id <> track_as_exercise_id)
);

-- ═══ PRESCRIPTION — an expression tree, not a literal ═══
CREATE TABLE prescribed_set (
  id            uuid PRIMARY KEY,
  block_item_id uuid NOT NULL,
  ordinal       int  NOT NULL,
  is_optional   boolean NOT NULL DEFAULT false,  -- excluded from compliance
  is_amrap      boolean NOT NULL DEFAULT false,
  UNIQUE (block_item_id, ordinal)
);

CREATE TABLE prescribed_target (
  prescribed_set_id uuid REFERENCES prescribed_set(id) ON DELETE CASCADE,
  metric_key        text REFERENCES metric(key),
  -- exactly one resolution strategy per row:
  literal_value     numeric,      -- 100 kg
  range_lo          numeric,      -- 6  ┐ generalises 'Rep Range' to ANY metric
  range_hi          numeric,      -- 8  ┘ → time ranges, RPE ranges, load ranges
  expr_kind         text,         -- pct_of_max|lwp_delta|pct_of_bodyweight|rpe_autoreg
  expr_arg          numeric,      -- 0.725 | 2.5 | 0.5 | 8.0
  expr_ref_exercise uuid,         -- override for pct_of_max
  PRIMARY KEY (prescribed_set_id, metric_key)
);

-- ═══ ASSIGNMENT — snapshot at publish. Non-negotiable. ═══
CREATE TABLE assigned_session (
  id                uuid PRIMARY KEY,
  athlete_id        uuid NOT NULL,
  source_session_id uuid,                -- provenance back to the program
  scheduled_date    date NOT NULL,
  state             text NOT NULL,       -- draft|published|in_progress|completed|skipped
  published_at      timestamptz,
  resolved_snapshot jsonb NOT NULL,      -- fully-resolved prescription AT PUBLISH TIME
  timezone          text NOT NULL        -- ATHLETE's tz, not the coach's
);

-- ═══ PERFORMANCE — independent of prescription ═══
CREATE TABLE performed_set (
  id                  uuid PRIMARY KEY,   -- CLIENT-GENERATED (offline-first)
  assigned_session_id uuid NOT NULL,
  exercise_id         uuid NOT NULL,      -- may DIFFER from prescription (swap)
  prescribed_set_id   uuid,               -- NULLABLE: athlete-added sets have no parent
  ordinal             int  NOT NULL,
  status              text NOT NULL,      -- completed|skipped|not_reached
  performed_at        timestamptz NOT NULL,
  client_created_at   timestamptz NOT NULL  -- offline conflict resolution
);

CREATE TABLE performed_measurement (
  performed_set_id uuid REFERENCES performed_set(id) ON DELETE CASCADE,
  metric_key       text REFERENCES metric(key),
  value            numeric NOT NULL,   -- ALWAYS in metric.canonical_unit
  PRIMARY KEY (performed_set_id, metric_key)
);

-- ═══ DERIVED STATE — append-only, never mutable columns ═══
CREATE TABLE working_max_event (
  id           uuid PRIMARY KEY,
  athlete_id   uuid NOT NULL,
  exercise_id  uuid NOT NULL,          -- ROOT exercise, after track_as resolution
  value_kg     numeric NOT NULL,
  source       text NOT NULL,          -- auto_estimate|coach_set|athlete_set|test_result
  formula      text,                    -- 'epley'|'brzycki'|'nsca_chart'
  from_set_id  uuid,
  effective_at timestamptz NOT NULL
);

CREATE TABLE pr_event (
  athlete_id       uuid NOT NULL,
  exercise_id      uuid NOT NULL,
  rep_count        int  NOT NULL,          -- PRs are PER REP-COUNT
  value_kg         numeric NOT NULL,
  achieved_at      timestamptz NOT NULL,
  performed_set_id uuid NOT NULL,
  PRIMARY KEY (athlete_id, exercise_id, rep_count, achieved_at)
);

What the registry buys you

Part D · Proposed schema

D4 · Resolution pipeline

How a target becomes a number an athlete sees. Runs once, at publish — never at render.

Resolving at publish rather than at render is the difference between an app whose history you can trust and one that silently rewrites itself every time a coach edits a template.
Part D · Proposed schema

D5 · Structured conditioning

The open flank. TrainHeroic's circuit block takes one result unit and 10,000 characters of prose — and the prose is invisible to every report they ship.

CREATE TABLE block (
  id            uuid PRIMARY KEY,
  session_id    uuid NOT NULL,
  ordinal       int  NOT NULL,
  category      text NOT NULL,  -- prep|speed_agility|skill_tech|strength_power|conditioning|recovery
  title         text,
  grouping      text NOT NULL,  -- single|superset|circuit  → drives A / A1,A2 / B1..B4
  scheme        text,           -- NULL|amrap|emom|e2mom|for_time|intervals|tabata|rounds
  scheme_params jsonb,          -- {cap_s:1200} | {interval_s:60,rounds:10} | {work_s:20,rest_s:10,rounds:8}
  score_metric  text REFERENCES metric(key),  -- rounds|duration|calories|distance|NULL
  is_test       boolean NOT NULL DEFAULT false   -- their "Test This Block"
);

✗ Their version

2-3 x E5OM

complete a 30m heavy farmers carry

Renders perfectly. Produces nothing. Not in volume, not in intensity, not in compliance, not in any export. A coach programming half their week as conditioning has half their week invisible.

✓ Structured

block {
  grouping: 'circuit',
  scheme: 'emom',
  scheme_params: { interval_s: 300, rounds: 3 },
  score_metric: 'rounds'
}
  └ block_item → Farmers Carry
      └ prescribed_set × 3
          ├ distance = 30 m
          └ load = pct_of_max(...)

Same render. Now it lands in the same analytics pipeline as a back squat, and an EMOM is a first-class object rather than a paragraph.

Part E · Decisions

E1 · Steal / reject matrix

Every notable TrainHeroic behaviour, with a verdict and a rating out of 10. Ratings are my judgement, and I'd defend each one.

BehaviourVerdictRatingReasoning
Reference Max indirectionSteal9"When loads are prescribed in %, the working max of this exercise is referenced." Solves variation programming better than anything else I've seen. Paused Bench at 70% resolving off Bench Press is exactly right.
Track As roll-upSteal9Results logged for X affect the history, working maxes and goals of Y. Variations feed the parent lift. Cheap to build, enormous for data density.
Weight (LWP+) autoregulationSteal8Last-weight-performed plus a delta, as a metric type rather than a separate progression engine. Elegant. Generalise it to expr_kind.
Block categories + block-level complianceSteal8Seven fixed categories doing triple duty — icon, section heading, and the unit of compliance. This is what makes "3/5 Blocks" mean something.
PRs per rep-countSteal8A 5RM and an 8RM are separate records with separate dates, and leaderboards only compare exact matches. Collapsing to one "best" throws away the useful signal.
Draft → publish + auto-publishSteal7Table stakes, but easy to forget. Coaches program in bursts and release on a schedule.
Prescription templatesSteal7Boring, high-leverage for anyone coaching more than about twenty people.
Parent CalendarsSteal7Master calendar that child team calendars inherit. Underrated — it's how multi-location gyms scale, and it's the enterprise wedge.
Optional set flagSteal7Tiny feature. It's the thing that makes compliance an honest number rather than a punishing one.

Session Comment as primary CTASteal6Making coach→athlete feedback the loudest button on the card is a deliberate retention choice. It works.

Part E · Decisions

E2 · Build order

Sequenced by what is unfixable later, not by what demos best.

Phase 0 · Decisions that are unfixable later

Do these before writing a line of product code. Each one is cheap now and a rewrite later.

  • Metric registry as a table, not an enum — with aggregation and is_load_bearing populated
  • Canonical units — everything stored in kg / m / s, converted at the edge
  • Client-generated IDs on every athlete-side write
  • Append-only working-max and PR event tables
  • Athlete timezone on the assignment, not the coach's

Phase 1 · The loop that has to work

  • Exercise library + equipment increments
  • Session builder — blocks, grouping, n-metric prescriptions
  • Assignment calendar + draft/publish + snapshot-on-publish
  • Athlete logging with offline outbox (this is the make-or-break; it's where TrainHeroic loses users)
  • Working max + PR derivation

Phase 2 · The reasons a coach switches

  • reference_max and track_as graph edges
  • Percentage + LWP resolution with equipment rounding
  • Compliance, volume (all three series), intensity — with the definitions shown in the UI
  • Structured conditioning schemes — AMRAP, EMOM, intervals, for-time
  • Prescription templates

Phase 3 · Moat

  • First-party cached video (the offline gap they cannot close)
  • Readiness with per-question polarity + custom questions
  • Parent Calendars for multi-location
  • Data export and a public API (they have neither)
  • DOTS-based leaderboards, documented
Honest caveats on this whole package

The metric-registry pattern is row-per-metric EAV — more joins than a wide table. At coaching-app scale (tens of millions of sets, not billions) this is fine, with a covering index on (performed_set_id, metric_key). If you later need speed, denormalise a jsonb cache column. Do not start there.

I have not seen TrainHeroic's actual schema. Section A4 is inferred from UI affordances and endpoint shapes; Part D is my design, not a reconstruction of theirs.

The formulas in C3 and C4 are mine. TrainHeroic's are undocumented. Don't cite them as "how TrainHeroic does it".
